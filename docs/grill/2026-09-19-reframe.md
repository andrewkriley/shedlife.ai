# Grill — 2026-09-19 reframe

A grill is a design interrogation: name the tensions, force a decision (or an
explicit deferral), then land the result in the PRD/SPEC/architecture. This file is
the record. The source of truth after it is [`../architecture.md`](../architecture.md),
[`../mvp.md`](../mvp.md), and the subsystem pairs it points at.

Input: The Shed as an agentic-first harness with three jobs (Assist, Build, Run);
four lifecycle phases (Bootstrap, Deploy, Build, Run); a curl-to-LXC bootstrap
that hosts a chat UI; predetermined playbooks; TDD; Galileo; the
`therileys-team` token set. MVP is Phase 1 only. Deploy / Build / Run each get
their own later grill.

## What was already true (keep)

- Product vs. tenant: this repo has no environment-specific content.
- Assist / Build / Run are a **routing dimension**, not agents. Domain sub-agents
  live in a registry.
- Fan-out / fan-in, independent verifier, loop prevention, `has_side_effects`
  approval — still the living-harness pattern.
- Secrets are fetched, not stored — **after** a secrets backend exists.
- Multi-user data model from day one; local password as one identity-provider type.
- Test-first for deterministic code; Galileo for LLM-facing behavior.
- The Core Agentic Loop already built (chat, SSE turns, classifier, `assist`,
  `run.network`, verifier, settings, Galileo traces) is reusable machinery, not
  scrap.

## Tension 1 — "Build" and "Run" mean two things

The three **jobs** of the living harness are Assist, Build, Run. The four
**lifecycle phases** of a tenant are Bootstrap, Deploy, Build, Run. Same words,
different jobs.

**Decision.** Keep both names — they match how the product is talked about — but
never let them collapse into each other.

- A **phase** is a chapter of standing a tenant up and then using it.
- A **job** is a classification dimension inside the running harness.
- In writing: "the Bootstrap phase" vs. "the Build job" whenever either could
  be misread.
- The Bootstrap assistant is a constrained Assist-job agent, not a fourth job.
- Phase 3 (Build) and Phase 4 (Run) *use* the Build and Run jobs. They are not
  a second product.

## Tension 2 — the old bootstrap was a fleet provisioner

The previous Bootstrap PRD ended at a k3s cluster, Flux, a Fleet repo, Infisical,
and The Shed as a reconciled workload — then **destroyed** the LXC. That is now
the shape of **Deploy** (and some of Build), not Bootstrap, and it is not MVP.

**Decision.** Bootstrap's job is the chicken-and-egg only:

1. A thin `install.sh` creates one LXC and prints a local URL.
2. That LXC *is* The Shed, in a **bootstrap profile**.
3. The UI is the chat. The assistant collects foundational facts, validates
   them, runs predetermined pre-deploy probes, and stores the result locally.
4. Nothing else is provisioned. No Proxmox cluster, no k3s, no Flux, no GitLab,
   no Infisical, no Fleet repo.

The former design is parked in [`../parked/`](../parked/), not deleted. It is
**not** source of truth until a Deploy grill says so.

## Tension 3 — "no installer mode" vs. a bootstrap web app

Architecture said: keep the first bootstrap outside the running app; no
special-case installer mode inside it. The new brief is a web app with an AI
assistant *in* the LXC.

**Decision.** The thin thing outside the app is only `install.sh` (create CT,
start the image, print URL). Everything after that *is* The Shed. The bootstrap
profile is a **constrained registry and local secret-zero**, not a second
codebase. That is a stricter reading of "no installer mode" than the old fat
LXC orchestrator, which was a provisioner that was not The Shed.

Whether the LXC later becomes break-glass, or the app migrates onto k3s, is a
Deploy-grill question. Phase 1: the LXC stays up.

## Tension 4 — reuse the loop, or write a slimmer bootstrap app?

A from-scratch SQLite chat would be smaller. The existing stack is Postgres +
Redis + FastAPI + React + the turn loop.

**Decision.** Reuse the existing app in a bootstrap profile. Postgres and Redis
run **inside the LXC** (compose or equivalent). "Store it locally" means the
data never leaves that CT — not "rewrite persistence." The collected
foundations are also exportable as a YAML bundle so Deploy has a typed input.

Short-circuit classification when the registry has exactly one agent (Phase 1:
`bootstrap.intake`). Do not delete the classifier.

## Tension 5 — the assistant cannot start without an API key

A Claude *subscription* is not a credential. The chat needs an Anthropic,
OpenAI, or Gemini **API key**. Putting that key in `curl | bash` is a worse
secret-handling story than a browser form on the LAN.

**Decision.** `install.sh` does not collect the key. The first web screen is a
**setup gate**: provider, API key (live-validated), operator email + password.
Then chat. Galileo is optional; missing keys keep the existing no-op tracer.

## Tension 6 — auto-open issues, but GitLab does not exist yet

**Decision.** Every unexpected error writes a **local issue record**, visible in
the UI, classified `operator-input` | `environment` | `product-bug`. Filing to
GitHub `andrewkriley/theshed` is opt-in and never includes secrets or raw probe
payloads. Tenant GitLab filing waits for Deploy. Validation failures are
field errors, not issues.

## Tension 7 — conversational UI vs. structured state

A freeform interview will drop the gateway.

**Decision.** The assistant is the driver; a **foundations schema** is the
store. The UI shows schema state (collected / valid / failing) beside chat.
Revisit, edit, re-run probes. Idempotent and state-aware. The model fills
records; it does not invent fields.

## Tension 8 — playbooks vs. a clever model

**Decision.** AI executes predetermined playbooks. It does not invent topology,
skip a validation, or "just ssh and see." Phase 1 playbooks:
`collect-foundations`, `validate-foundations`, `predeploy-probe`,
`export-state`. Deploy playbooks do not exist yet.

## Tension 9 — Proxmox cluster in Bootstrap or Build?

The brief puts a 3/5-host Proxmox cluster under the Build phase. The old PRD
formed the cluster during bootstrap.

**Decision.** Phase 1 prerequisite is **one** Proxmox host. Bootstrap may record
*intent* that more hosts exist. Forming the cluster is a later Build-phase
grill. Withdrawn from Bootstrap.

## Tension 10 — TLS and `Secure` cookies on a LAN HTTP URL

Auth SPEC requires `Secure` cookies. Phase 1 is `http://<lxc-ip>` on the LAN.
`Secure` cookies will not be sent.

**Decision.** Bootstrap profile: HTTP on the LAN, cookies `HttpOnly` +
`SameSite=Lax`, `Secure` **off**. Accepted LAN-trust tradeoff. Not an
internet posture. TLS, Let's Encrypt, Cloudflared, Traefik: Deploy grill.

## Tension 11 — Galileo's SDK vs. native provider SDKs

The brief: assistants built "inline with Galileo's SDK for OpenAI, Anthropic
and Gemini." Galileo wraps OpenAI (sync) and documents native Anthropic/Gemini
plus manual spans. This repo already traces via `galileo_context` and a native
async Anthropic client. Galileo's OpenAI wrapper does not support `AsyncOpenAI`.

**Decision.** Keep native SDKs for Anthropic, OpenAI, and (new) Gemini, with
the existing Galileo span instrumentation. Do not put Galileo's OpenAI wrapper
in front of the async/streaming path. Add Gemini as a first-class provider.
Claude subscription remains unsupported.

## Tension 12 — design tokens vs. what's in the frontend

`brand/tokens.json` already matches `therileys-team` (same canvas/panel/accent
roles). The running CSS is still the Vite default, including a light path.
`therileys-team` is dark-only and does not merge with `shared.json`. Accents
are mid-bright: filled surfaces use `bg.canvas` text, not white.

**Decision.** `therileys-team` is the token set. Vendor or fetch from
[andrewkriley/design-system](https://github.com/andrewkriley/design-system)
(`design-system/tokens/therileys-team.json`). Resolve `{a.b.c}` references.
Dark only. Implementation is a Phase 1 UI requirement, not a later polish
item.

## Tension 13 — shedlife.ai

Domain secured, not active. Product marketing name. Not a required tenant
hostname and not baked into the product repo as config.

## Tension 14 — Let's Encrypt, Traefik, Cloudflared, Grafana, Prometheus

Flagged in the brief, explicitly out of MVP.

**Decision.** Capture as Deploy open questions. Do not pick HTTP vs. DNS
challenge, do not add Traefik, do not design cert renewal here.

## What the other subsystems become

| Subsystem | After this grill |
|---|---|
| Core Agentic Loop | Still the harness. Phase 1 uses it as a single-agent bootstrap profile. Cross-macro fan-out and the three-sub-agent success criteria move to post-Deploy. |
| Auth | First user comes from the setup gate, not a Fleet apply. Cookie model stands; `Secure` off in bootstrap. |
| Secrets | Local secret-zero in the LXC, same client interface. Infisical + Kubernetes Secret home wait for Deploy. |
| GPU / compute | Still valid. Deferred to the Build-phase grill (local AI cluster). |
| Release pipeline | Still valid. The bootstrap LXC pulls the same GHCR image. Fleet-repo pull is Deploy-era. |

## Open questions this grill will not answer

1. Let's Encrypt: HTTP-01 vs. DNS-01; how renewal works with k3s and everything
   else; what is automated. (**Deploy grill.**)
2. Is Traefik needed, or does something else terminate? (**Deploy grill.**)
3. Cloudflared's role relative to local DNS and public names. (**Deploy grill.**)
4. Grafana / Prometheus (and later Splunk) vs. Galileo — infra metrics vs. LLM
   traces. (**Deploy / Build grills.**)
5. After Deploy succeeds: does the bootstrap LXC retire, stay as break-glass,
   or become a node? (**Deploy grill.**)
6. Brownfield DNS record migration. (Already deferred; still deferred.)
